# 当我们在讨论大模型性能优化的时候，我们在说什么？
基于 TPU 简单描述一种优化模型性能的角度。

本文使用 AI 辅助排版和润色，但作者对文章内容负责。

总结:
大模型性能优化问题可以简化为优化大模型在指定硬件上的整网利用率（理论下界时间与实测时间之比）, 并且可以借用信息熵的概念来量化模型性能优化中遇到的问题复杂度.

## 目标

大模型性能优化的目标，是在精度达标、资源给定的前提下，尽可能提高吞吐。

> 1. 精度达标指的是，最终模型测评结果达到预期（如 ARC-AGI-2 等基准测试）。
> 2. 由计算顺序改变（融合、拆分、Reduce 等）引起的精度误差，我们认为在精度可接受范围内。
> 3. 资源给定指的是给定 TPU 硬件；网络拓扑这类可动态改变的不算给定。

吞吐落实到具体指标，即 token/s 或 train_step/s。这一目标清晰且可量化，但缺少方向性，需要进一步拆解。

在真实的推理与训练场景中，吞吐这一指标还需考虑并行度、TTFT、TPOT、P99、内存限制等因素；这些因素归结为两类约束：时延类指标（TTFT 为 prefill 时延预算、TPOT 为每步时延、P99 为尾部时延约束）既压缩并行度上限、也给时间项加上界；内存限制通过容量约束压缩可行并行数。

考虑上述条件，可以拆解为：**吞吐 = 并行数 / 时间**。

以上均与具体模型无关。

需要说明的是，并行数并不是一个可以独立调优的简单维度。并行策略（TP/PP/EP/FSDP 的切分方式）本身就是计算图变换，与计算图高度相关，因此这里并入计算图要素一并考虑，本文暂不展开。

## 时间的拆解：五个要素与熵

模型时间由众多复杂因素组合而成。这里借用信息论中"信息熵"的概念度量各因素的复杂程度，并给出形式化定义：

**熵 = 在固定文法下，从全体合法排列中定位一个或一种候选所需的平均比特数（= log₂|S|）。**

- S 为文法下的全体合法排列（代码排列组合）集合；
- 直觉含义：搜索开始前，"解是哪一个"的先验不确定性；
- 文法必须被显式定义（什么是一种排列：计算图的排列 / tile 配置 / 计算指令的排列 / 通信的指令排列以及拓扑 / 调度的先后排列），否则 |S| 不可计算；
- 熵值越高，搜索空间越大；但达到目标的难度取决于达标解的密度 |A|/|S|（见后文推论），而非 |S| 本身。

在这里给出 TPU 上影响模型时间的五个要素大类：
1. **HBM（DRAM）↔ VMEM（SRAM）的搬运时间。** 在**输入输出参数给定**的情况下，能打满利用率的 tile 配置相对较少, 且合法的 tile 配置也较少。
   1. 不同硬件上的名词可能不同，本质是高速存储与低速存储之间的搬运时间。
   2. 在别的硬件微架构上，内存搬运可能变得相当复杂，这取决于搬运涉及的硬件 IP 数量。
   3. 如果考虑到整个模型中保证数学等价的合法 tile 配置，复杂度会暴涨。
2. **计算单元（MXU / VPU）与 VMEM 之间的计算时间。** 在**输入输出参数、公式以及硬件 ISA 给定**的情况下，能达到峰值算力利用率的指令排列较少，基本只会有固定的写法；合法的指令排列虽多，但在 ISA 的帮助下可以快速收敛。
   1. 如果只给定数学公式和硬件 ISA、不给定输入输出参数的 shape（可 fusion/split），复杂度也会暴涨。
3. **通信时间。** 对通信本身而言，**固定网络拓扑和固定通信算法**下的最短时间原则上可求；但**拓扑的可选方案很多**，且**通信算法本身的排列组合**非常多，并且与并行策略高度相关，不同的排列组合还可能有不同的性能友好区间。
4. **同步与调度导致的 stall 时间。** 想要把 stall 降到最低，基本**无法求出全局最优解**，因为它往往与并行策略、以及各并行的搬运/计算/通信时间相互耦合——stall 时间是个结果。
5. **计算图。** 计算图本身直接导致的时间很小（内存管理、资源竞争之类），大头在于计算图会影响上面 4 个要素；其排列组合若不加限制便趋于无限——可以任意拆分与并行，可以任意安排计算次序——因此必须由文法显式有限化（见下），否则熵与达标难度均不可定义。

其余因素，在大模型性能优化中占比通常不高，或可被上述五个要素涵盖：

- runtime / kernel launch
- host 侧计算开销（计入计算时间与数据搬运时间）
- 内存分配与释放（计入 runtime）
- 计算不均衡（计入同步与调度）
- 资源竞争（计入计算图）
- 内存管理（计入计算图）
- cache（计入计算时间；TPU 无用户可见数据 cache）
- warm-up（计入 host 侧）

### 计算图：排列与有限性

计算图的一个"排列"，指在保持数学等价的前提下，对计算图做的三类组合变换：

- **fusion**：合并相邻算子；
- **split**：把算子沿某轴拆分（并行切分也属此类）；
- **reorder**：交换/结合重排计算次序；

此外还有可选的重计算（以计算量换内存）。若形状与 tile 尺寸不做量化（允许任意 padding、任意切分粒度），S_图 无限，熵无定义；即便量化后，S_图 也随模型规模超指数增长。

但模型 shape 是有限的：切点只能在有限维度上选取、融合只能合并有限节点、重排只在有限节点之间排列，"任意切分与并行"最终被形状整除性与节点数封顶。因此存在一个显式文法（限定拆分粒度与次数、固定算子集合）使 S_图 有限，熵与达标难度因此良定义。

> 五个主要要素相互耦合，单独谈论"某要素的熵"没有意义；从整个模型来看，这五个要素的熵都很大，所以**没有多少之分**。不过在实际工程中，我们会层层拆解，不断拆解复杂度和不确定性，最终可以写成链式法则下的条件熵分解：

```
H(总) = H(图) + H(通信|图) + H(stall|图,通信) + H(计算|前三者) + H(搬运|前四者)
```

每一项的含义是"其余要素固定之后，仍需提供的决策比特数"。由此可得，"熵小是因为被固定了更多因素"；注意，上述链式分解顺序可变，故该顺序不蕴含重要度。

## 归纳：从全局最优到高利用率

对上面拆解的五个要素做总结归纳，可以得到下面的结论：

1. 五个类别本质是从不同角度影响**不同硬件单元的运行时间**——模型最终是要跑在硬件上的。
2. 条件熵较小的部分，是因为在真实场景中被其他环节消除了不确定性（这正是条件熵的定义）；条件熵较大的部分约束更少。真实场景中每个因素都与其他因素或多或少相互影响，因此从级别上并不存在大小之分。
3. 模型优化中存在大量相互影响的因素，每个因素的熵值都很大、复杂度很高，寻找全局最优解基本不可求。
4. 基于 1：无论计算图如何等价变换，其计算量与数据搬运量一定存在一个最小界限，并且硬件单元的性能也存在一个最高上限。
5. 基于 1、3、4：全局最优解不可求，所有因素都从不同角度影响硬件单元的运行时间，且计算量与搬运量存在下界——那么从工程角度出发，我们不追求整个模型的全局最优解，而是追求指定模型在特定硬件上的较高**整网利用率**（定义见下），把基本不可解的问题转化为层层约束下的利用率求解问题。

此外，这里给出两种口径的利用率：
- **单因素利用率**：（该 IP 承担的工作量 / 该 IP 峰值能力）/ 整模型时间——即单个硬件 IP（MXU / VPU / HBM 通道 / ICN 链路）的理论下界时间占整模型时间的比例（MXU 取矩阵 FLOPs、HBM 取强制流量，余类推）。本文取 80% 作为判定瓶颈 IP 已饱和的门槛。
- **整网利用率**：理论下界时间由计算与搬运两项合成——**理论下界时间 = max(计算量下界 / 峰值算力, 强制流量 / 峰值带宽)**（两个下界的定义见下方"参考下界"）——**整网利用率 = 理论下界时间 / 实测时间**。在模型、算法与硬件给定的前提下，最大化整网利用率与最小化时间等价，本文取 60% 作为达标线。

两种口径统一采用时间比值：分子（计算量下界与强制流量）是与具体方案无关的固定常数，因此无用计算只会拉长实测时间、压低利用率，不会虚增分子。工程做法即：尽量减少无用计算，让瓶颈硬件单元尽量饱和、其余尽量被隐藏，或达到指定约束下的上限（如显存、延迟约束）。

**推论（达标难度）**：设达标线为指定的整网利用率门槛（本文取 60%），A 为达到门槛的合法排列集合（H(A) = log₂|A|），则均匀随机搜索命中达标解的期望次数为 |S|/|A| = 2^(H(总) − H(A))。达标难度 = H(总) − H(A) 比特：达标线宽松时 A 大、难度低；达标线贴近容量约束时 A 坍缩、难度回升。工程上的"难"由实例自身的 H(总) − H(A) 决定；NP-hard 只是精确求解的最坏情况性质（见"方法"一节），与这里的实例难度是两个视角。

### 参考下界（理想化）

计算量与搬运量的最小界限可以通过纯数学模型与指定硬件算出，理想化假设为：

- 不考虑重计算、算法族固定：计算量下界 = 算法本身的精确 FLOPs，可直接算出；
- HBM/VMEM 容量无限：搬运量下界 = 强制流量（每个字节读写各一次），可直接算出。

两者分别除以峰值算力与峰值带宽后取 max，即整网利用率的理论下界时间：**理论下界时间 = max(计算量下界 / 峰值算力, 强制流量 / 峰值带宽)**。

注意，这套假设删去了容量约束，因此由这两个下界合成的理论下界时间过于理想，任何真实系统的整网利用率都达不到 100%。工程上应取实测谱上的经验上限（如 HBM 通道的单因素利用率 85%–90%）来校准整网利用率的目标值；我们希望尽量靠近理论下界，并对中间的 gap 作出可信且细致的解释。

## 方法：cost model + RCPSP + 图改写搜索

基本思路是量化：通过 cost model 量化每个代码段对不同硬件单元的影响。一个 kernel 可拆分为若干代码段（如向量单元执行的 1D 代码段、矩阵单元执行的 2D 代码段），量化各代码段的时间后，基于计算图重新排列组合。

更进一步的策略是把 fusion/split 纳入考虑：在保持计算图数学等价的前提下增删代码段——fusion 可视为删除 HBM → VMEM 代码段，split 可视为增加 HBM ↔ VMEM 代码段。

代码段对硬件单元的影响中，有的直接影响时间（如 2D/1D 计算量），有的间接影响（如 VMEM/HBM 占用）。多个代码段组合还需量化组合效应：某代码段超出显存容量，需增加 HBM ↔ VMEM 读写代码；某代码段 VMEM 未溢出，且 MXU 与 VPU 无依赖，可以 overlap，时间因此减少。

**问题抽象**：这个问题可以抽象为**带资源约束的项目调度（RCPSP）+ 图改写搜索**：

- 代码段之间存在依赖约束，不能自由排列组合；
- 时间目标不可加：并发段取 max，串行段取 sum；
- 资源约束是多维的（VMEM / 寄存器 / 带宽 / DMA 槽位），且互相争用。

在此抽象下，整模型时间 = RCPSP 实例的 makespan。RCPSP 是 NP-hard，因此"层层约束下的求解"降级为"层层约束下的启发式搜索"，与"较高整网利用率"的目标一致。

NP-hard 是精确求解的最坏情况性质；工程上只需达到"较高整网利用率"，实际搜索难度由达标解的密度决定：达标线宽松时达标解密集、搜索容易；达标线贴近容量约束时达标解稀疏、搜索困难。经验上，autotuner 能以数百次评估在巨大空间中命中"够好"的 kernel，说明该实例族的达标密度在实践中并不极端。难度集中出现在尾部病态形状（不可整除维度、ragged batch），即 |A| 最小之处。

cost model 的准确性建立在以下假设上：

1. TPU 是足够简单的硬件（无用户可见 cache 层级、固定频率、无 warp 发散、ISA 固定）；
2. 可以获得全部源码：从 XLA 的 HLO 优化 / fusion / layout / SPMD 切分，到 XLA TPU 后端的 LLO 代码生成与 libtpu runtime 层，全部可读可改，编译器决策规则可以完整复刻，而非从采样中拟合；
3. 以芯片厂商的视角出发，硬件侧常数可得：HBM bank 冲突、读写 turnaround、功耗墙行为等，经由 RTL、周期精确仿真与后硅表征获得；
4. 评估成本可由 AI 加速：假设 1–3 构成一个廉价而精确的"标签生成器"（全源码 + 硬件模型 → 离线生成海量精确标注），以其训练学习型 cost model 代理，把"编译/仿真每个候选"摊薄至近似零成本。

在假设 1–3 成立的边界内（即芯片厂商内部视角），cost model 可视为已解决；学习型代理会引入自身的模型误差，但假设 1–3 提供海量精确标签用于离线训练，该误差可被压至工程可接受水平；残余风险有两类：代理随编译器升级的漂移（见开放问题 1），以及搜索生成训练分布之外的新候选时的泛化误差——后者是版本内的分布外问题，无法靠训练分布内的标签消除。

## 优化方向

1. **自底向上**：从被更多前提固定、条件熵较小的部分（如给定 shape 后的计算与搬运）向约束更少、条件熵较大的部分（如计算图）优化。例如计算部分在特定约束下能相对简单地达到较高单因素利用率（如 MXU ≥ 80%），便可反过来约束上层——只允许给出能维持该利用率的参数，进而优化上层的计算图与通信/搬运策略。精确的表述是：利用硬件 ISA 等已经确定的信息，反向消除其他因素的不确定性。
2. **自顶向下**：从约束更少、条件熵较大的部分（计算图）向被更多前提固定的部分（搬运/计算）优化。熵既是复杂度也是自由度：通过调整计算图，自上而下地调整数据流搬运与计算部分，利用自由度较大的优势寻找收益点。

两者互补迭代，而非二选一。

## 量化：短板与关键路径（两个公式）

这一目标可以被量化，主要借助计算短板与计算关键路径两种方式。

通过纯粹的计算与足够准确的 cost model，可以得出不同策略下整个模型的预估时间。随后以预估时间为标准，经由不同方法与角度（如上一节的两个方向）提高整网利用率。

### 公式一：瓶颈式（并行数足够）

当并行数足够多、不同并行之间可以相互 overlap，直至瓶颈硬件 IP 的单因素利用率在整模型范围内达到 80% 门槛时，时间可简化为：

```
time = max(数据搬运量 / 带宽 / 搬运效率,
           计算量 / 算力峰值 / 计算效率,
           通信量 / 通信能力 / 通信效率,
           ...)
```

其中各"效率"是相应硬件 IP **忙碌期内的实际吞吐与峰值之比（段内效率）**，由 cost model 给出；它与单因素利用率的关系为：单因素利用率 = 段内效率 × 忙碌时间占比，瓶颈 IP 忙碌占比接近 100% 时两者近似相等。当搬运项代入强制流量、计算项代入计算量下界、各效率取 100% 时，右端（忽略通信项）即理论下界时间；实际搬运量超出强制流量、效率低于 100% 的部分，正是 gap 的来源。目前在 TPU 上，时间主要取决于所有可并行硬件 IP 的运行时间中最慢的一项。主要由数据搬运、计算、通信这三个可重叠因素组成；若存在其他并行因素，可追加到其后，如 host memory ↔ device memory 这类。

适用条件：需要足够的独立并行度支撑 overlap，使瓶颈 IP 的单因素利用率达到 80% 门槛以上；解码这类串行依赖、无可重叠并行的场景不适用。

（说明：此处的 80% 是单个硬件 IP 的单因素利用率门槛，用于判定瓶颈 IP 的下界时间是否主导整模型时间（即进入饱和稳态）；与"达标难度"推论中 60% 的整网利用率达标线是两个不同的量。）

### 公式二：关键路径式（并行数不足）

当并行数不足时，时间主要由以下形式组成：

```
time = sum(关键路径上各硬件 IP 的 工作量 / 峰值能力 / 段内效率)
```

非关键路径上的其余 IP 都应被关键路径掩盖；若掩盖不住，则时间最长的路径成为关键路径。

注意：这是给定调度之后的描述式——求使 makespan 最小的调度正是 RCPSP，本身 NP-hard。

**统一视角**：上述两个公式是 RCPSP makespan 的两个极端 regime——资源充裕（完全 overlap）时 makespan → max(...)，资源稀缺时 makespan → 关键路径 sum。

## 开放问题

1. **代理的漂移与再训练**：学习型 cost model 在编译器升级后需要重新生成标签、重新训练；再训练成本决定框架对上游变化的适应速度。
2. **并行度与计算图搜索的接口**：并行策略并入计算图之后，外层调优（内存峰值预算）与内层搜索（时间预算）如何交替迭代。
3. **能否由模型生成候选替代启发式搜索**：当前目标是对计算图的优化，能否训练一个大模型来直接完成"寻找排列组合"的过程，以模型生成候选替代启发式搜索。
